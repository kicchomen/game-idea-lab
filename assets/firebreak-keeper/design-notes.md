# 火の見の番人 / Firebreak Keeper

## 役割から選ぶ

プレイヤーは山あいの集落の防災隊長。地図を見て、2人の隊員の行動順を決める。「目の前を消す」「延焼の通り道を切る」「その間に住民を助ける」を組み合わせる体験を選んだ。現実の防災・火災対応を教えるものではなく、すべて架空のルール。

検討候補は、飛行郵便の仕分け、単線鉄道の信号番、山林の防災指揮。郵便は反射神経と分類だけに寄り、単一の交差点を使う鉄道は一台ずつ出せば解ける危険があった。防災指揮は、複数の目的・有限の水・移動・環境変化の先読みを同じ地図で結びつけられるため採用した。

## 直近の企画との違い

- Sensor Shift: センサーを編集して再生する。今回は隊員が世界の中で移動・介入し、状況が累積的に変わる
- Footstep Echo: 自分の遅延した足あとと協力する。今回は2隊員の行動予算と、予告される環境変化を配分する
- Tiny Tug: リアルタイムに操船して長い曳航列を扱う。今回は反射操作がなく、進行をプレイヤーが決める
- Night Market: 在庫と売買を扱う。今回は価格・収益・取引を持たず、空間的な遮断・範囲消火・救助の指揮を扱う

主動詞は「指揮する」。操作対象は2隊員と地形。時間は明示的なターン進行。フィードバックは炎の縮小・防火帯・救助済みの印。勝利は3組の救助と全火点消火の両立。リトライは1手undoまたは任務全体の再挑戦。

## 面白さの仮説

最初の5〜10秒: 隊員を選ぶと移動可能なマスが光る。範囲放水で複数の火が一度に消え、家に救助済みの印がつく。

10分後: 広域放水をまとめて使う位置取り、水の補給へ戻る時機、次の風向き、防火帯で失う1行動と得られる時間の交換を考える。3任務で初期火点と水量を変える。これは設計意図であり、10分間の実人プレイで面白さを検証したという意味ではない。

1時間後の企画展開（未実装）: 任務ごとの役割が異なる隊員、橋や尾根により分断される移動経路、複数地区の優先救助、変化する風の情報精度。単に面数を足すのではなく、情報の読み方・分担・帰路確保が変わる展開を考える。現行試作が1時間の遊びを提供するわけではない。

## 実装範囲

- 7×7、2隊員、3軒、1隊員2行動/ターン
- 移動は最短の通行可能経路で2マスまで。燃えているマスは通過不可。隊員同士や家との重なりは許可
- 放水はマンハッタン距離2以内の指定マスを中心に3×3。1水消費。火または延焼予告を範囲に含む指定だけ有効
- 放水後、森と家は2回の延焼判定で保護される
- 隣接（自分のマス含む）の森を防火帯にする。水消費なし、1行動
- 家の上/隣から救助。井戸の上/隣から水を3回分まで補給
- 風下1マスへ延焼。偶数ターンは風と垂直な方向へも延焼。火は3回の延焼判定後に消える。森は灰に
- 点線は次に火が移るマスの正確な予告。古い火が消えるターンも最後に延焼する
- 未救助の家が燃えた時点で失敗。救助後の家は焼けても続行可
- 隊員のマスが燃えると道路の初期位置へ退避し、水を1失う。退避後の次ターンは通常の2行動
- 3組救助＋火が0＋焼失した森8マス以内で勝利。9マス目で即失敗。任務ごとの最終ターンを進めた時点で未達なら失敗
- 3任務、undo、再挑戦、任務選択、キーボードZでundo（長押しリピート無視）
- リアルタイム処理がなく、ブラウザを離れても時間は進まない。保存・通信・アカウント・解析・外部依存なし

## PDCA 1

Plan: 消火に集中するだけではなく、救助・移動・補給との順序を考える最小体験を作る。次に起こることは明示し、失敗原因を読めるようにする。

Do: 3任務と純粋なJavaScriptルールエンジン、DOMの地図UI、undo、範囲放水、防火帯、救助を実装。

Check: 最初の放水対象判定は「中心に火がある」か「予告が範囲にある」だけを許可していた。任務2の実行ルートで、中心は空でも周囲の火に放水したい合法な操作が拒否された。

Act: 3×3範囲内に実際の火または延焼予告がある場合は、中心が空でも放水可能に変更。回帰テストを追加。

Re-check: 初回24件のNodeテストに合格。ルールエンジンを実際に操作する固定入力で、任務1は3ターン10行動、任務2は4ターン14行動、任務3は6ターン19行動で勝利。任務3の確認ルートでは補給と防火帯を使用。最短・最適解を主張しない。

## 未検証・次の問い

Nodeテストはブラウザ表示・実機タッチ・初見理解・面白さを検証するものではない。ブラウザQAは別途記録する。

- 初見の人は「救助だけでなく火を0にする」勝利条件を理解できるか
- 防火帯は放水・自然消火に比べて、有意味な選択肢になっているか。確認ルートに登場しても必要性は証明されない
- 任務3で補給が負担になりすぎず、先回りの手応えにつながるか
- 7列の地図は狭いスマホで誤タップしやすくないか。undoが十分な救済になるか
- 火が減る快感、救助完了、隊員の分担は魅力として成立するか

数値バランスとゲームとしての持続的な面白さは未確定。この公開試作は成立性を小さく調べるためのもの。


## PDCA 2: 放置で勝てる抜け道

Check: 独立したコードレビューで、先に3組を助け、その後は森全体が自然に燃え尽きるまで待つと任務2/3で勝てることを確認。消火・防火帯を選ぶ動機が勝利条件から抜けていた。

Act: 全任務で焼失した森は8マス以内という制約を加え、9マス目で失敗するよう変更。目標文・ルール・HUDで同じ条件を明示。全3任務に「救助して待つ」失敗回帰を追加。既存の成功ルートは維持され、焼失数は0 / 0 / 2マス。

また、終了後に隊員/行動を選ぶと結果説明が上書きされる問題を防ぎ、終了時のボタン無効化とイベントガードを実装。隊員退避の通知が通常のターン説明で消されないようにした。狭幅の結果パネルは装飾を減らし、内容が長ければ内部スクロールする。

Re-check: 29件のエンジンテスト＋4件のモックDOMコントローラテスト、計33件が合格。コントローラでは実操作コマンド列による成功、終了後の操作固定、成功/失敗からのundo、再挑戦、任務切り替え、長押し反復無視を確認。ビジュアルブラウザQAは別途必要。防火帯が常に必要・最適であることは未証明であり、次のプレイテストの問いとして残す。
