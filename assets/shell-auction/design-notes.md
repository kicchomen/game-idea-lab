# 貝がらの競り市 — 体験設計と小さな試作

2026-10-27。実装は `games/shell-auction/`。これは競りとセット収集の核を確かめる小規模なブラウザー試作であり、長く遊べる完成作の実証ではない。

## 選んだ体験

海辺の市で、自分の展示棚をつくる収集家になる。目の前の貝は欲しい。でも、あとに来る青い貝にもコインを残したい。隣の収集家が何に高い札を出したかを思い出し、「ここは譲る」「この組み合わせの最後の1枚には出す」を決める。

主動詞は **見立てる・入札する・譲る・そろえる**。全員の合意をつくる仲介ではなく、1品を誰か1人しか手にできない競争が中心。負けてもお金は減らないが、相手の予算と所持品が変わり、その後の価格競争も変わる。過去の操作を消して同じ場面を再生するのではなく、1つの市場の中で6回の取り消せない判断を重ねる。

### この形を選んだ理由

候補「貝の競り」を、値上げ式の競り・固定価格の買い物・封印入札の3つの構造で検討した。候補数を満たすための別名案は追加しない。

- 値上げ式なら、相手が降りるまで1枚ずつ上げるだけの手順にしないために、降りるタイミングや相手の不確実性をもう少し丁寧に実装する必要がある。
- 固定価格の買い物は価格の読みや競合相手の反応が弱く、「夜市の仕入れ番」の在庫選択に近づく。
- 今回は封印入札を採用。相手の今回の札は隠れ、開札後には全員の札が残る。勝つための上乗せと、過払いで次を失う危険を1回の判断にまとめられる。ただし、ブラフや自由会話による心理戦は実装していない。

これはジャンル全体としての新発明という主張ではない。既出試作からの構造的な距離と、遊ぶ人の役割を優先した選定。

## 正確なルール

- プレイヤー24枚、リオ18枚、ナギ18枚。途中の収入・借金・売却はない。
- 扇貝・巻き貝・月貝に桃／青の2色。各組み合わせ1枚ずつ、全部で6品。全出品順は開閉できる予定表で最初から見られる。
- 各品に0〜手持ち全額の整数を入札する。0は見送り。全員の札を同時に開き、最高額の1人が **自分の入札額** を払う。負けた人の支出は0。
- 同額の優先は「あなた→リオ→ナギ」「リオ→ナギ→あなた」「ナギ→あなた→リオ」を繰り返す。現在の順は確定前から公開。全員0なら不落で、無料で貝は配らない。
- 貝1枚2点。同形2枚で追加4点（形ごと）。3形を各1枚以上で追加5点（1回）。依頼の色を2枚以上で追加5点（1回）。すべて重複する。
- 6品終了時16点以上で成功。相手との得点順位ではない。余ったコインは点にならない。
- リオはどちらかの色、ナギはどれかの形を好む。好みは画面に直接出さず、過去の全入札と所持品を記録する。
- 相手の札は `2 + 好み加算 + 同形所持加算 + 品ごとの微差` を残金で上限化する。好み加算はリオ4／ナギ5、同形所持は2、微差は0〜2。好み・微差・出品順・依頼色はseedで固定。**相手は今回のプレイヤー入札を読まない。** リオ／ナギの自分のかごと残金だけが途中で反映される。
- 相手は最適戦略を学習するAIではない。好きな形をすでに持つことによる加算はあるが、プレイヤーの長期計画を妨害しようとはしない。

## 5秒・10分・1時間の広がり

以下は設計意図と未検証の仮説であり、初見の人の観察結果ではない。

- **最初の5〜10秒**：競り台の大きな貝、手持ちコイン、札の金額が見え、金額を選んで札を開ける。「負けるとお金は減らない」「同額でも席順で勝者が変わる」という手応えを1回の開札で知ることを狙う。スコアの細則を最初から全部記憶させない。
- **10分の深さ**：出品順から欲しい3〜4枚を見立てる。同じ形のペアで増やすか、3種類＋依頼を狙うか。相手の好みに合う品を見送り、お金を使ってもらうか。前回は勝ったが払いすぎた品を安く狙えるか。違うseedで同じ固定額が通用しないことを確かめる。実際に10分飽きずに遊ばれた証拠はまだない。
- **1時間以上へ向けた企画（未実装）**：複数の市場で展示を持ち越し、次の市へ出すコレクションを選ぶ。公開の競りと封印入札を使い分ける会場、収集家との貸し借り・交換、複数人の対戦、希少品を売るか展示に残すかという長期判断。単なる品数追加ではなく、情報の公開範囲・所有の意味・継続関係が変わる方向を想定する。

現試作だけで1時間の奥深さを主張しない。既知の市場は記憶でき、対人の読み合いでもない。

## 今回、実装したこと／していないこと

**実装済み**：6品の封印入札、異なる好みを持つ2相手、全員の有限財布・所持品、公開の同額優先、セット得点と色依頼、入札履歴、出品予定、成功／失敗、同seed再挑戦、新seed、URLの `?seed=` で再現、途中やり直しの確認、ネイティブボタン／rangeによる操作。

**未実装**：対人戦、適応・会話AI、札の駆け引き演技、複数市場の旅、展示配置、売却・交換、保存／ロード、音、実績、ランキング、ネットワーク同期、アカウント、課金、分析送信。ゲームの実行中に外部へ通信しない。

**見た目**：HTML/CSSの競り台、庇、木の縁、収集家の簡素な肖像。貝は自作インラインSVG。ダッシュボードの同じ重さの箱を並べるのではなく、今の1品と札を出す動作を中央に置き、記録・予定・ルールは折りたたむ。別ファイルの生成表紙は企画イラストであり、この実画面のスクリーンショットではない。

## 実装境界と操作保護

- 既存READMEの方針を継承し、依存ライブラリ・ビルド・CDN・外部フォントなし。Phaserなどの追加は、この静的配布の制約と小さな文字中心の競りには不要と判断。
- `engine.js` はDOMを持たない不変状態遷移。Node CommonJSとブラウザーの同じコードを使う。`app.js` は表示・入力だけを担当する。
- `bid → reveal → bid`。最後の開札も確認後に `ended` へ進む。結果を読まずに一度のクリックで2品進めない。
- revision検査・取り外されたDOMの拒否・確定間の400msガード・ダブルクリックdetail・Enter/Space長押し抑止を実装。スライダー操作ではDOMを再作成しないため、ドラッグの途中で入力対象が消えない。
- 結果・次品・終了の見出しへフォーカスを移し、その見出しを即時スクロール表示。金額変更だけではスクロールしない。ライブ領域は再描画する部分の外に置き、同じ文を繰り返し再通知しない。
- 途中やり直しは確認あり。取消で元の操作にフォーカスを戻す。確認中は入札／見送り／次へを見た目でもdisabledにする。
- 全ボタンは最小44px幅／46px高。280px以下は入札／見送りを縦にして、256pxの入れ子表示でも小さい横並びボタンを作らない。320/360/390pxの実測は親担当のブラウザー検証と区別する。
- reduced-motionに対応。音・タイマー・保存なし。ブラウザー／端末を閉じれば進行は失われる。

## PDCA

### Plan / Do

「欲しい品を全部買えない」「同じ初期額の連打では足りない」「相手に譲ると後の状況も変わる」を純粋エンジンで試す。初期案は手持ち22枚、他2人18枚。収集は単品の価値だけでなくペア・3形・色依頼の組み合わせで評価する。

### Check：22枚だと、一部の市場に成功経路がない

作者の `probe-0`〜`probe-999` 探索では22枚時に985市場だけ成功可能。独立レビューでも22枚版 `independent-0`〜`independent-499` の500市場中14市場が最大15点だった。例 `independent-10`・`independent-18`・`independent-21`。これはプレイヤーの学習不足ではなく、全情報を知っても16点へ届かない市場なので修正対象にした。

探索は各品で「0で見送る」か「同額優先込みの最小落札額で勝つ」だけを分岐する。負け入札は見送りと結果が同じ、余分な過払いは自分の将来予算だけを減らすので、このモデルではこの分岐で最大到達点を調べられる。人が情報を見て選ぶ戦略の評価ではない。

### Act / Re-check：24枚に変更

手持ちを24枚へ変更。作者の1,000市場、独立レビューの `independent-0`〜`independent-4999` の5,000市場では、すべてに16点以上の経路が見つかった。元の不可解seedも回帰テストにした。これは **有限サンプルでの到達性** であり、任意文字列のseed全体についての数学的保証ではない。

初期市場は、最小落札／見送りに絞った41合法経路のうち4経路が成功、最高21点。経路数は人の勝率ではない。実際の入札額は複数あり、過払い許容も含まない。初見の難しさは人で確かめる必要がある。

24枚版 `probe-0`〜`probe-199` の200市場で、毎回同じ額（残金不足なら残額）を入れた自動比較：

| 固定入札 | 16点以上の市場数 | 平均得点 |
|---|---:|---:|
| 見送り0 | 0 / 200 | 0 |
| 3枚 | 0 / 200 | 1.69 |
| 5枚 | 0 / 200 | 6.675 |
| 6枚 | 10 / 200 | 9.695 |
| 7枚 | 22 / 200 | 12.465 |
| 8枚 | 34 / 200 | 12.94 |
| 9枚 | 35 / 200 | 12.63 |
| 12枚 | 0 / 200 | 6.13 |
| 全額24枚から | 0 / 200 | 2 |

これらは最適な情報利用方針との公平な技能比較でも、人によるプレイテストでもない。ただし、安価な固定札でも高い固定札でも単純に全市場を制覇できる設計ではないことを確認できた。

### 入力とUIの確認

作者テスト中、金額変更でrevisionを更新した後に、やり直しボタンのrevisionが旧値に残る点を修正。表示中の全ボタンを同期し、金額変更後にも確認・取消が使える回帰テストを追加。

独立レビューで、開札中にやり直し確認を出すと「次へ」はハンドラで拒否していても外見が有効のままだと指摘された。確認中は次へにもdisabledを付け、作者の回帰テストを追加。相手に渡った貝の枚数・予算、同額優先、過払い額、0札の扱い、見送り後の次品を合わせて確認した。

実ブラウザーからの修正・幅の実測・公開版の確認は別の親担当記録を参照する。この文書はそれらの実施前にコードから合格を宣言しない。

## 通常操作で再現できる経路

市場番号 `shiosai-1027`。各品で金額を＋ボタンまたはスライダーで選び、「N枚で札を出す」。0は「見送る」。開札後は「次の品を見る」、6品目は「展示を仕上げる」。

- **21点成功**：`3 → 5 → 0 → 7 → 7 → 0`。桃月・桃巻・青巻・青月を集め、貝8点＋2ペア8点＋依頼5点。残り2枚。
- **別の16点成功**：`3 → 0 → 0 → 9 → 0 → 11`。桃月・青巻・青扇。貝6点＋3形5点＋依頼5点。ペアは0。残り1枚。
- **惜しい15点失敗**：`0 → 0 → 9 → 0 → 5 → 9`。桃扇・青月・青扇。貝6点＋1ペア4点＋依頼5点。巻き貝がないため3形の加点なし。残り1枚。
- **0点失敗**：6品すべて見送り。残24枚でも点数に換算されない。

同じseedで再挑戦すると出品・好み・微差は同一。途中の落札者が変われば相手の所持・財布も変わるので、後の相手の札は必ず同じになるわけではない。

## 自動検証の境界

`node --test tests/shell-auction*.test.cjs`。作者側は純粋エンジン27件、実際のapp.jsをDOM代替で動かすコントローラー16件。独立側はエンジン14件・DOM代替11件。計68件（この記事時点）。既存全体も合わせて再実行する。

検査対象：不変性、初期条件、全6品の一意性、seed再現、相手が現在の札を読まないこと、公開同額優先、全額・0・不正値、予算保存、セット得点、二つの成功経路と15/0点失敗、重複確定拒否、終了後拒否、再挑戦、確認取消、古いDOM、入力継続、表示用seedのescape、見出しのフォーカス／スクロール呼び出し。

DOM代替テストはCSS描画・実クリック座標・タッチ・ブラウザーのフォーカス挙動・スクリーンリーダーを検証しない。実機スマホ、他ブラウザー、初見の人による理解・面白さ・10分後の満足度は未確認。

次に人で確かめたい点：

1. 「落札者だけ自分の額を払う」と「同額の公開優先」を最初の開札で理解できるか。
2. 負けた記録からリオ／ナギの好みを推測し、次の札を変えるか。単に安い順に買うだけにならないか。
3. 全出品順を見たうえで、ペア中心と3形中心の2つの展示方針を自分で考えられるか。
4. 15点失敗が理不尽でなく、次の1手を考える材料になるか。
5. スマホで予定・履歴を開閉する負担と、金額操作から結果を見る距離は適切か。

面白さの観察が足りないまま、品数やキャンペーンを増やして深さが出たことにはしない。
