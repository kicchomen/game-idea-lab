# 水車町の一週間 / The Waterwheel Week

2026-10-25。この記事用の小規模なゲーム試作。実装は `games/waterwheel-week/`。

## 選んだ体験

プレイヤーは水車町のお祭りに向け、7日間でパン21個を用意する。1日1枚だけ工房カードまたは資材獲得カードを選び、その日の夕方から工房が自動生産を始める。建てたものは消えず、翌日も同じ仕事をする。「今、得をする」だけでなく「明日も繰り返し働く仕組みを育てる」が主役。

中心になる判断は、麦畑を増やすか、水車の加工量を増やすか、パン窯を増やすか、それとも建設を1日見送って資材を補うか。工房は生産の順番が決まっており、余剰の麦や粉を翌日へ持ち越せる。能力を足すだけでは増産にならない場合があるため、予測で材料不足を見る。

## 他案との比較と選定

- 今回採用：水車町のエンジンビルド。毎日の出力が次の建設判断に影響し、以前の選択が繰り返し働く。既存の短いアクション試作と異なる、時間をかけた設備投資の感覚を狙う。
- 候補：隣接する建物の相性を競う街づくり。空間配置が中心になり、既存「つながる小さな森 / Pocket Forest」の隣接・接続パズルに寄りやすいため今回は不採用。
- 候補：毎晩パンの仕入れを決める店番。「夜市の仕入れ番 / Night Market」の有限在庫・注文・需要判断との重なりが大きく、今回は不採用。
- 候補：荷車へ材料を積み込む物流。形と空き領域が主題となり、`packing-truck` の配置・回転体験に近くなるため不採用。
- 既存の交渉「旅人たちの取り引き」、時間制御「小さな駅の発車係」、戦闘系「火花の盾」とも、相手への提案・反応、締切内の操作、攻撃対応ではなく「恒久設備の収益を蓄積する」点で区別する。

比較根拠は同一リポジトリの README と各エンジン。ジャンル全体としての新規性を主張するものではない。

## ルールと数値

- 初期資源：コイン6、木材6、麦0、粉0、パン0。麦畑1つを所持。
- 毎日3枚の固定候補から1枚だけ選ぶ。カード選択は予測、別の確定ボタンが実行。
- 建設費を支払う／資材を受け取る → 畑の収穫・木材生産 → 麦を粉に加工 → 粉をパンに加工 → 町の収入コイン2、の順。
- 工房は建てた当日から働く。余った資源は翌日に持ち越す。
- 麦畑：コイン2・木材2。毎夕、麦2。
- 水車小屋：コイン3・木材2。毎夕、麦2までを同数の粉にする。
- パン窯：コイン4・木材2。毎夕、粉2でパン3。半分のバッチでは焼けない。
- きこり小屋：コイン1・木材1。毎夕、木材2。
- 資材の手伝い：無料。直ちにコイン1・木材4。工房は増えない。
- 7日目の夕方、パン21個以上で成功。20個以下は失敗。パンの売買や隠れた需要はない。

毎日の候補：

1. 水車小屋 / きこり小屋 / 資材の手伝い
2. パン窯 / 水車小屋 / 資材の手伝い
3. 麦畑 / きこり小屋 / 資材の手伝い
4. 水車小屋 / パン窯 / 資材の手伝い
5. パン窯 / 麦畑 / 資材の手伝い
6. 水車小屋 / パン窯 / 資材の手伝い
7. パン窯 / 麦畑 / 資材の手伝い

## 5秒・10分・1時間の仮説

未検証の体験仮説であり、ユーザーテストの結果ではない。

- 最初の5秒：川沿いの畑・水車・窯と「7日でパン21個」を見て目的がわかる。今日の候補に触れると、まだ確定せず夕方の見通しだけを見られる。ただし、スマートフォンではカード選択から予測まで縦スクロールが必要であり、初見で気づけるかを確認したい。
- 10分：最初の7日間を終え、18個で足りなかった理由や、増設しても材料不足で休む理由を把握する。同じ固定条件で、前回と異なる建設順を1〜2回試したくなることを狙う。
- 1時間：現実装の固定7日間だけで1時間遊べるとは見込まない。長期化するなら、週別の注文目標、限られた建設場所、異なる加工系列など、出力の大きさ以外にも決断を変える変化が必要。いずれも未実装。

## 試作範囲

実装済み：1つの固定シナリオ、5種類の選択肢、7日、材料・設備・生産順、成功と失敗、1日ごとの記録、途中の確認付きリトライ、結果からの再挑戦、マウス／タップ／キーボード操作、予測、材料不足の説明、CSSの狭幅レイアウト、全7日間の固定候補予定表。

未実装：保存・ロード、ランダムカード、複数シナリオ、音、ランキング、実績、オンライン、課金、外部API、可変価格、住民AI、建設位置の自由配置、工房の売却、巻き戻し。完成品や長期的なエンジンビルドの奥深さを示すものではない。

静止した町の絵はDOM内の自作SVGで、施設所持に応じて濃淡が変わる。建設ごとに建物を1棟ずつ追加する映像ではなく、実際の基数は文字で示す。Bloggerカバー等の生成画像は別途管理し、このSVGや実画面と混同しない。

## 技術と操作

- 依存ライブラリ、ビルド、第三者フォント、ゲーム内ネットワーク通信なし。
- `engine.js` はDOMを持たない純粋な状態遷移と生産計算。ブラウザの `WaterwheelEngine` とNodeのCommonJSで同一実装を使用。
- `app.js` は表示・入力のみ。予測と本番確定が同じ生産計算を利用する。
- `phase` は choose → report → choose、7日目は ended。夕方結果を別操作で確認しないと翌日に進まない。
- `revision` は選択変更・確定・翌日・リトライで増え、古い画面の確定を拒否。
- 連続確定の400msガード、ダブルクリックdetail、Enter/Space/数字の長押しrepeat対策。タイマーの制限時間ではない。
- 数字1〜3で予測。TabとEnter／Spaceで通常のボタン操作。ライブ領域で選択・結果を通知。reduced-motionを尊重。
- 最小ボタン高は46px、主操作48px。320/360/390 CSS px用に横幅内へ収まるスタイルを実装。実ブラウザの幅計測と描画品質は別検証であり、コードだけで合格とはしない。

## PDCA 記録

### Plan

「以前に建てた設備が毎日働く」ことを、最小3段階の生産連鎖で伝える。初期の目標候補はパン24個。資材だけ集めても成功しない、1つずつの基本設備だけでも必ず勝てない数値を探す。

### Do

7日固定の3択と資源計算を実装。合法な全ルートを純粋エンジンで列挙し、最終パン数・勝敗・資源負数・予測の一致を検査。UIは先に予測し、別操作で日を終える方式にした。

### Check

24個を必達にすると、初期資源コイン6・木材6で合法な1,864通りのうち到達は10通りだけだった。基本設備を1日目水車・2日目窯で建てて以後拡張しないと18個。実装済みの生産順では、序盤に残った粉を追加の窯で使う21個ルートと、畑・水車・窯を拡張する27個ルートがどちらも成立する。

全ルート数や成功数は初見の人の勝率ではない。合法な列を均等に数えた組合せの記録であり、無意味な補給を繰り返すルートも含む。

### Act

必達を21個へ下げ、24個以上を再挑戦時の改善目標に変更。現設定では合法1,864ルート中139ルートが成功、最大27個。カード選択を非破壊の予測にし、材料不足を文章化。選択変更のrevision、夕方確認ゲート、長押し・連打対策、途中リトライ確認を追加。最終日の結果では「明日に持ち越す」と言わず、7日間の生産終了を明記する。

独立ソースレビューで「固定候補が先に見えないと複数日の計画を立てにくい」「途中リトライ取消時にフォーカスを失う」と指摘されたため、開閉できる「これから届くカード」で全7日間の候補を公開し、今日・過去を明示。取消時のフォーカスを元のやり直しボタンへ戻すよう修正した。予定表は解答や最適手を出さない。

親タスクの実ブラウザ確認で、320pxの成功ルートは成立した一方、選択画面の低い位置で確定すると結果見出しが上方へ移り、従来のpreventScroll指定で結果を見失うことが判明した。render(focusId)の状態遷移時のみ、見出しへfocusしたあとscrollIntoView({block: start})で表示するよう修正。カード選択時の予測フォーカスはスクロールを維持し、実装側テストで結果・翌日・終了・再挑戦のスクロール対象を確認した。実ブラウザでの修正後再確認は親タスクの別記録に委ねる。

次の改善判断は実ブラウザおよび初見の人で行う。特に、スマホでカードと予測を往復する手間、麦・粉・パンの流れの理解、きこり小屋が候補として魅力的かを確かめたい。

- 21個成功：水車小屋 → パン窯 → 資材の手伝い → パン窯 → 資材の手伝い → 資材の手伝い → 資材の手伝い。

### 埋め込みのスクロール再修正

親タスクのPages検証で、高さ1900pxの同一origin iframeでは結果見出しがiframe内592pxにあっても外側viewportでは上方に隠れるケースが残った。状態遷移時にfocusの自動スクロールを抑え、scrollIntoViewをinstant指定にしたうえで、同一originのframeElementが取得できる祖先のみ、iframe枠位置＋見出し位置から外側windowのスクロール位置を計算する方式へ変更。2重iframeでも実際のスクロール増分を反映して座標を伝播する。アプリのキャッシュ更新用URLはapp.js?v=20261025-scroll2。

追加のNode検査は、1900px相当の高いiframeの座標算術、2重iframe、異なるoriginでframeElement=nullとなる境界、SecurityErrorの封じ込め、キャッシュ版クエリの5件。実ブラウザの描画検証とは別。実装側48件＋親の独立算術3件で計51件合格。Bloggerのように異なるoriginの親ページは直接スクロールせず、標準scrollIntoViewまでで停止する。記事側で外側へのスクロール連携が必要なら、iframe高さ調整または明示的なホスト側実装を別途検討する。

仕様参照：MDN [scrollIntoView](https://developer.mozilla.org/en-US/docs/Web/API/Element/scrollIntoView) と [frameElement](https://developer.mozilla.org/en-US/docs/Web/API/Window/frameElement)。
